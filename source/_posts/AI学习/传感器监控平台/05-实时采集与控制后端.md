# 第 5 篇：实时采集与控制后端

> **本篇目标**
> 用一个 FastAPI 服务把驱动包起来：**后台定时采集 → 缓存最新值 → 通过 WebSocket 推给网页**，
> 同时暴露一组控制接口给网页上的按钮用。
>
> 预计 **25 分钟**。

---

## 一、这一层要解决的问题

驱动写完之后，你其实已经能读数据了。但那只是「一次调用读一次」。后端要解决三件事：

| 问题 | 解决方式 |
| :--- | :--- |
| 网页不可能自己每秒去读串口（浏览器碰不到串口） | 后端**后台线程轮询**，把结果缓存起来 |
| 网页要「实时」，轮询 HTTP 又慢又浪费 | 用 **WebSocket**，有新数据就推 |
| 网页上的按钮要真的能控设备 | 一组 **REST 控制接口**，写入后立即回报 |

![实时数据流](/images/传感器监控平台/04-dataflow.svg)

**两条链路，互不阻塞：**

- **采集链路**：后台线程 → 轮询驱动 → 解码 → 写缓存 → 广播给所有 WebSocket 连接
- **控制链路**：网页 POST → 校验参数 → 写寄存器 → 立即返回结果 → 顺带刷新一次缓存

> ⚠️ **关键约束**：两条链路都会碰串口，所以**必须共用驱动层那一把锁**（[第 4 篇](/2026/09/16/AI学习/传感器监控平台/04-三个传感器驱动开发/) 做的）。否则一读一写同时进行，两边都收到 CRC 错误。

> ▶ **怎么启动服务**：在 VSCode 里打开 `run.py`，点右上角 **▶** 就直接起服务
> （默认读 `config.yaml`，也就是模拟器模式，不用敲任何参数）。
> 需要 `--with-simulator`、`--port 8000` 这类参数时，点 ▶ 右边的 **▾** 选对应启动项。
> 命令行备选见 [导读 · 第六节](/2026/09/16/AI学习/传感器监控平台/README/)。

> WorkBuddy → **「允许完全访问」** → 新建任务 → 整段复制。

````text
# 任务：为 RS485 传感器项目实现 FastAPI 后端（采集 + 推送 + 控制）

## 背景
项目根目录 = **当前工作目录下的 `sensor-hub` 子目录**。开工前先 `Get-Location` 确认；
如果我在这段对话里另行指定了路径，以我指定的为准；
**不要写死盘符或用户名路径**，并在你输出的第一行先报告实际使用的绝对路径。
已完成：
  · app/modbus_base.py —— ModbusConnection（支持 serial / tcp，内置 threading.Lock 串行化，gap_ms 最小命令间隔）
  · app/devices.py —— LightSensor / UltrasonicSensor / AlarmDevice
  · app/simulator.py —— 本地 Modbus TCP 模拟器（127.0.0.1:5020，从机 1=光照 2=超声波 3=报警器）
  · tools/ 下若干调试工具；config.yaml 含 transport / poll_interval / serial / simulator / devices
  · docs/protocol.md —— 厂商接口文档的协议摘要（**所有取值范围、换算、特殊值都以它为准**）
待实现：app/hub.py、app/server.py、run.py（一键启动）

> ⚠️ 接口里的校验范围、单位、特殊值，**一律从 `docs/protocol.md` 取**，不要凭印象写数字。

## 一、app/hub.py —— 采集调度与缓存
实现 `SensorHub` 类：

1) 构造时接收 config dict，按需创建三个驱动实例（config["devices"][key]["enabled"] 为 false 则不创建）：
   light / ultrasonic / alarm。驱动实例通过 ModbusConnection.from_config(cfg, key) 建立连接。
2) 提供 start() / stop()：
   · start() 启动一个后台守护线程，按 config["poll_interval"]（默认 1.0 秒）循环采集
   · 循环体：调用 _collect_once()，然后 sleep 到下一个周期（用 Event.wait 以便立即响应 stop）
   · stop() 设置 Event 并 join 线程（带超时），最后关闭所有连接
3) _collect_once() 采集内容：
   · 光照度：LightSensor.read_illuminance()
   · 超声波：UltrasonicSensor.read_all()
   · 报警器：AlarmDevice.read_state()
   每个设备的失败不能中断其他设备（逐个 try/except，失败就把该项标记为 error 并记录原因）
4) 缓存：维护 self._snapshot（dict），结构固定如下（前端会依赖这个结构，不要随意改字段名）：
   {
     "ts": 1726464000.123,                # 采集时刻的 Unix 时间戳（秒）
     "ok": true,                          # 本轮是否至少有一个设备读成功
     "errors": ["alarm: timeout"],        # 本轮失败项的人类可读原因，无失败则为空数组
     "light":      {"ok": true, "illuminance_lux": 20019, "device_address": 1, "baud_code": 3},
     "ultrasonic": {"ok": true, "processed_mm": 754.0, "realtime_mm": 751.0,
                    "temperature_c": 30.0, "echo_us": 4336, "status": "ok",
                    "range_level": 4, "angle_level": 4, "denoise_level": 1},
     "alarm":      {"ok": true, "sound": true, "light": true, "volume": 30,
                    "folder": 1, "track": 1, "play_mode": 1,
                    "flash_sync": 1, "flash_mode": 1,
                    "total_folders": 1, "total_tracks": 8}
   }
   读取失败的设备，其子字典写成 {"ok": false, "error": "原因"}（其余字段可省略）。
   （注：上面的 `baud_code` 是**设备寄存器里的波特率编码**，由驱动读出，来自你的协议摘要；
    它和 config.yaml 里的 `baudrate`（串口通信参数，如 9600）不是同一个东西，别混用。）
5) 线程安全：对 self._snapshot 的读写都要加锁（可以用单独的 threading.Lock，不要和串口锁混用）。
6) 订阅机制：提供 subscribe(callback) / unsubscribe(callback)。
   每轮采集完成后，把最新 snapshot 交给所有订阅者（订阅者异常要吞掉并记录，不能影响采集线程）。
7) 提供 get_snapshot() -> dict（返回深拷贝，避免调用方误改）。
8) 提供 reload() -> bool：重新读取 config.yaml 并重建连接（供以后扩展用，先实现基本逻辑）。

## 二、app/server.py —— FastAPI 服务
1) 用 lifespan（或 startup/shutdown 事件）在应用启动时 hub.start()，关闭时 hub.stop()。
2) 挂载静态目录：把项目根下 static/ 作为静态资源；`GET /` 返回 static/index.html。
3) REST 接口（全部返回 JSON；统一结构 {"ok": bool, "data": ..., "message": str}）：

   GET  /api/health
        → {"ok":true,"data":{"transport":"simulator","uptime_s":123,"devices":["light","ultrasonic","alarm"]}}

   GET  /api/snapshot
        → 返回 hub.get_snapshot()

   GET  /api/config
        → 只返回**安全字段**：transport、poll_interval、各设备是否启用、slave_id。
          【绝对不要返回串口号之外的系统信息，也不要返回任何密钥】

   POST /api/alarm/switch       body: {"on": true}              → 全开 / 全关
   POST /api/alarm/volume       body: {"level": <合法值>}        → 取值范围取 docs/protocol.md
   POST /api/alarm/track        body: {"folder": 1, "track": 3}
   POST /api/alarm/mode         body: {"mode": <合法值>}
   POST /api/alarm/flash        body: {"sync": <合法值>, "mode": <合法值>}
   POST /api/ultrasonic/config  body: {"range_level": 3} | {"angle_level": 2} | {"denoise_level": 2}
        可一次传多个字段，只写传了的那些。

   要求：
   · 用 pydantic 模型定义请求体，做类型与范围校验。
     **各字段的合法取值范围一律从 `docs/protocol.md` 取**，不要凭印象写数字；
     越界返回 422 或 {"ok":false,...}
   · 所有写操作执行完后，**立即触发一次 hub 的单项刷新**，并把最新值放进 data 返回，
     这样前端不用等下一个轮询周期就能看到变化
   · 参数非法时返回 {"ok":false,"message":"<说明范围要求的具体提示>"}，不要抛 500

4) WebSocket：`/ws/stream`
   · 连接建立后立即推送一次当前 snapshot
   · 之后每当 hub 采集完成就推一次（用 hub.subscribe 注册回调）
   · 实现方式注意线程安全：后台线程不能直接 await 到 WebSocket，
     请用 `asyncio.run_coroutine_threadsafe` 或一个 asyncio.Queue + 独立消费协程
   · 客户端断开要正确清理订阅，避免内存泄漏
   · 推送消息格式：{"type":"snapshot","data":{...snapshot...}}

5) 【安全开关】默认**禁用**写设备地址 / 写波特率这类危险操作。
   在 config.yaml 增加 `allow_dangerous_ops: false`；只有当它为 true 且环境变量
   `SENSOR_ALLOW_DANGEROUS=1` 同时满足时，才注册下面两个接口（否则返回 403）：
   POST /api/light/device-address   body: {"address": 1..252}
   POST /api/ultrasonic/config-danger  改波特率等
   同时在 README.md 里写清楚：改地址时必须保证总线上只挂一台设备。

6) 日志：用 logging，输出到控制台，格式含时间、级别、模块。轮询失败不要打 ERROR 刷屏，
   改成「连续失败 3 次以上才告警、恢复时提示」的策略。

## 三、run.py —— 一键启动
- 支持 `uv run python run.py`（默认 transport=simulator，可用 --transport serial 覆盖）
- `--host`（默认 127.0.0.1）`--port`（默认 8000）`--reload`
- 支持 `--with-simulator`：在同一进程内先启动模拟器再启动 Web 服务（方便演示；
  注意模拟器要用独立线程/进程，别把事件循环堵住）
- 启动后打印：访问地址、当前 transport、启用了哪些设备
````

## 四、三个容易踩的坑

**坑 1：在后台线程里直接 `await websocket.send_json()`**
后台轮询线程不是 asyncio 线程，直接 await 会炸。正确做法：
```python
loop = asyncio.get_event_loop()
asyncio.run_coroutine_threadsafe(queue.put(snapshot), loop)
```
或者干脆用 `asyncio.Queue`，让一个协程专门消费。

**坑 2：轮询线程和控制接口抢串口**
虽然基类有锁，但如果你在 `server.py` 里绕过驱动直接调 pymodbus，锁就失效了。**永远走驱动方法。**

**坑 3：轮询间隔设太小**
报警器的命令间隔要求 >300ms。如果你把 `poll_interval` 设成 0.1 秒，而报警器每轮都读一次，很可能触发设备的间隔限制。
**建议 `poll_interval ≥ 1.0` 秒**；报警器这种慢设备可以单独降低采集频率。
