## 一、设计原则

![从接口文档到驱动代码](/images/传感器监控平台/03-protocol-flow.svg)

**四条规矩，写之前先记住：**

**1）驱动只负责「翻译」**
`read_illuminance()` 只做一件事：把寄存器原始值翻译成 Lux。它**不关心**谁来调、多久调一次、要不要发到网页上。

**2）异常也算数据**
设备返回的**特殊值 / 状态码**（比如厂商定义的「干扰」「未检测到物体」）**不是错误，是设备在说话**。
驱动要把它们翻译成 `None` 或状态枚举，而不是当成读取失败。**具体有哪些特殊值，看 `docs/protocol.md`。**

**3）每个数值都要有换算依据**
读到 `0x4E20` 到底是多少？靠的是摘要里的**换算公式**（系数、单位、是否跨寄存器、是否有符号）。
写代码时把公式的来源注释在方法旁边，**别让"魔法数字"散落在逻辑里**。

**4）读和写共用一把锁**
串口是**独占**资源。采集线程在轮询的时候，如果控制接口同时往串口写，两边的帧会**交错**，结果是两边都收到 CRC 错误。**必须在基类里放一把 `threading.Lock`，所有读写都从它过。**

````text
## 第 1 步（必做）：先确认 pymodbus 的实际 API

## 二、app/modbus_base.py —— 统一基类
要求：

1) 一个 `ModbusConnection` 类，构造参数：
   transport: "serial" | "tcp"、以及对应的连接参数（串口：port/baudrate/parity/stopbits/bytesize/timeout；
   TCP：host/tcp_port）、slave_id、retries（默认 2）、retry_delay（默认 0.2）、gap_ms（默认 0，最小命令间隔）
   并提供一个类方法 `from_config(cfg: dict, device_key: str)` 从 config.yaml 的内容构造实例：
   - 当 cfg["transport"] == "simulator" 时走 TCP，连 cfg["simulator"]["host"]/["port"]
   - 当 cfg["transport"] == "serial" 时走串口，参数取 cfg["serial"]
   - slave_id 与 baudrate 优先取 cfg["devices"][device_key] 里的值，缺失再回落到全局

2) 内部持有一个 `threading.Lock`。**所有读写方法都必须先拿锁**，保证串口不被并发使用。
   还要实现一个内部方法 `_enforce_gap()`：如果 gap_ms > 0，则保证距上次通讯至少间隔 gap_ms 毫秒。

3) 对外方法（全部返回可判定的结果，不抛裸异常）：
   - connect() -> bool
   - close() -> None
   - is_connected -> bool（属性）
   - read_holding(address: int, count: int) -> list[int] | None
   - write_register(address: int, value: int) -> bool
   - write_registers(address: int, values: list[int]) -> bool
   读取/写入失败时返回 None / False，并把原因记到 logging（用模块级 logger，不要用 print）。
   内置重试：失败后按 retries 次数重试，每次间隔 retry_delay；仍失败才返回失败。

4) 异常处理：捕获 ModbusException 与串口异常；
   如果是 Modbus 异常响应（ExceptionResponse），要解析出异常码并翻译成人话：
   01=非法功能码 02=非法寄存器地址 03=非法数据 07=CRC校验错误
5) 模块级工具函数：
   - to_signed16(value: int) -> int        把 0~65535 转成有符号 int16
   - to_unsigned16(value: int) -> int      反向转换
   - format_frame(values) -> str           把寄存器列表格式化成 "0x0001 0x00FF" 便于打印
6) 提供 `if __name__ == "__main__":` 的自测入口：从 config.yaml 构造实例，连接，
   读 1 个寄存器，打印结果，断开。

## 三、app/devices.py —— 三个传感器驱动
每个类都继承自一个小基类 `BaseSensor`（可放在本文件顶部），BaseSensor 持有 ModbusConnection 实例。

> ⚠️ **下面每一台设备的寄存器地址、数据类型、换算公式、取值范围、出厂默认值，
> 一律从 `docs/protocol.md` 里查，本提示词不提供。**
> 我给出的是**方法清单和实现要求**——"要哪些功能、要满足什么约束"；
> "寄存器长什么样"是你要从文档里读出来的。

### 类 1：LightSensor —— 光照度变送器（设备名见 config.yaml 的 `devices.light`）

需要的方法：
- `read_illuminance() -> int | None`   读取光照度。**注意它可能跨多个寄存器、可能是有符号/无符号**，
                                      一切按摘要里的数据类型与换算公式来
- `read_raw() -> tuple[int, ...] | None`  返回测量用到的原始寄存器（便于排错）
- `get_device_address() -> int | None`
- `set_device_address(addr: int) -> bool` 参数范围校验（范围取摘要），非法直接返回 `False` 并说明原因
- `get_baud_code() -> int | None`
- `set_baud_code(code: int) -> bool`      只允许摘要里列出的合法取值
- 在类里定义常量：`REG_MEASURE_HIGH` / `REG_MEASURE_LOW` / `REG_ADDR` / `REG_BAUD`
  —— **常量名按上面这几个来，值全部取自 `docs/protocol.md`**，并在每个常量后写注释注明出处
- 如果摘要里记录**厂商给出的官方读值样例**，把它写成一个断言（见第四节自测第 3 条）

### 类 2：UltrasonicSensor —— 超声波测距模组（`devices.ultrasonic`）

需要的方法：
- `read_distance_processed() -> float | None`  处理值距离，单位 mm；遇到摘要里标注的异常值返回 `None` 并记录原因
- `read_distance_realtime() -> float | None`   实时值距离，单位 mm
- `read_temperature() -> float | None`         单位 ℃，保留 1 位小数
                                               ⚠️ **先确认摘要里这个量的数据类型是不是有符号**，
                                               否则冬天会读出 6553.5℃
- `read_echo_time() -> int | None`             回波时间；单位与换算方式以摘要为准
- `read_all() -> dict`                         一次读测量区（+ 需要单独读的寄存器），返回：
  `{"processed_mm":…, "realtime_mm":…, "temperature_c":…, "echo_us":…, "status": "ok|<异常状态名>"}`
- `read_status_flag(raw: int) -> str`          把摘要里标注的特殊值翻译成状态字符串；
                                              建议用模块级字典 `SPECIAL_VALUES = {…}` 定义映射
- `set_range_level(level: int) -> bool`        取值范围取摘要
- `set_angle_level(level: int) -> bool`        取值范围取摘要
- `set_denoise_level(level: int) -> bool`      取值范围取摘要
- `get_range_level()` / `get_angle_level()` / `get_denoise_level() -> int | None`
- 在类里定义常量：测量区 `REG_*`、配置区 `REG_*`、特殊值 `VAL_*`，
  以及波特率代码映射 `BAUD_MAP`（如果摘要里给了这张表）——**值全部取自 `docs/protocol.md`**

### 类 3：AlarmDevice —— 声光报警器（`devices.alarm`）

需要的方法：
- `read_state() -> dict | None`   一次读状态区，返回
  `{"sound": bool, "light": bool, "volume": int, "folder": int, "track": int,
    "play_mode": int, "flash_sync": int, "flash_mode": int, "raw": [...]}`
  —— 具体哪些字段是位域、哪些是整体数值，按摘要解析
- `read_status_word() -> int | None`
- `set_sound(on: bool) -> bool`   单独控制声音位（**保留灯光位不变** —— 用"读-改-写"，不要直接覆盖整个寄存器）
- `set_light(on: bool) -> bool`   单独控制灯光位
- `switch(on: bool) -> bool`      一键全开 / 全关
- `set_volume(level: int) -> bool`  校验范围（取摘要）
- `set_track(folder: int, track: int) -> bool`  按摘要里的编码方式拼成一个寄存器值
- `set_play_mode(mode: int) -> bool`            只允许摘要里列出的合法取值
- `set_flash(sync: int, mode: int) -> bool`     按摘要里的高/低位定义组合成一个值
- `read_total_tracks() -> tuple[int, int] | None`
- 在类里定义常量（含摘要里给出的**出厂默认值**）

**关于命令间隔**：摘要里若有「两条命令之间的最小间隔」这类硬性要求，
必须通过给该设备的 `ModbusConnection` 设置 `gap_ms` 来满足
——**不要在各个方法里散落 `time.sleep()`**，那是治标不治本。

**关于型号差异**：厂商文档里可能描述了**多种型号**（例如普通 485 型 / 带颜色位的三元信号型），
它们的位定义不一样。本项目**按普通型实现**，同时要求：
- 定义模块级常量 `ALARM_TYPE = "normal"`
- 在 `set_sound` / `set_light` 内部预留 `if ALARM_TYPE != "normal":` 的分支占位（写 `TODO` 注释即可）
- 把你从文档里读到的**型号差异写进 `docs/protocol.md` 的备注**，方便以后适配

## 四、自测要求（必须实际执行）
1. 先启动模拟器：`uv run python -m app.simulator`（放到后台，或用 Start-Job）。
2. 把 config.yaml 的 transport 设为 simulator，运行 `uv run python -m app.modbus_base`，
   贴出真实的读取结果。
3. **官方样例对账（重要）**：从 `docs/protocol.md` 的「原文样例」里取出厂商给出的读值样例，
   写一个断言证明你的换算公式能复现它（不匹配就把结果贴出来并说明你怀疑谁错了）。
4. 写一个临时脚本（可放 tools/ 下，命名 check_devices.py），依次调用：
   - LightSensor.read_illuminance()
   - UltrasonicSensor.read_all()
   - AlarmDevice.read_state()
   贴出真实输出，确认三个类都能通过模拟器拿到数据。
5. 写操作验证：对报警器选一个数值寄存器写入新值后读回确认；再改一个位域寄存器，
   确认**只影响目标位**。把「写入前 → 写入后」贴出来。
6. 异常值验证：让模拟器注入摘要里标注的异常值，确认对应读方法返回 `None`
   且 `status` 显示成摘要里定义的异常状态名；再注入一个**负的**有符号量，确认符号处理正确。
7. 输出自检报告：
   | 验证项 | 期望 | 实际 | 通过？ |
   覆盖：协议摘要来源（三份文档路径）、官方样例复现、各测量值读数、有符号量与换算、
   报警器位域读写、异常值处理、并发锁是否生效（可简单说明实现方式）。

## 约束
- 不要用 print 做日志，统一用 logging；但自测脚本可以 print 给人看。
- **全部从零实现**：不要复制粘贴任何既有脚本，也不要让项目 import 它们。
- **一切寄存器地址、数据类型、换算公式、特殊值，以 `docs/protocol.md` 为准**
  （那份摘要由你从厂商接口文档读出）；**不许凭记忆、不许上网搜**。
- 所有寄存器地址写成类常量，不要散落在方法里。
- 缺少摘要里没有的信息时**停下来问我**，不要猜。
- 真实命令和真实输出，禁止编造。失败如实汇报。
````

## 三、⭐ 提示词 B：三个独立调试脚本

驱动类写完之后，再让智能体给每个传感器配一个「傻瓜式」调试脚本——**插上线就能跑，一眼看出对不对**。

````text
# 任务：为三个传感器各写一个独立调试脚本

## 背景
项目根目录 = **当前工作目录下的 `sensor-hub` 子目录**。开工前先 `Get-Location` 确认；
如果我在这段对话里另行指定了路径，以我指定的为准；
**不要写死盘符或用户名路径**，并在你输出的第一行先报告实际使用的绝对路径。
已有 app/modbus_base.py、app/devices.py（三个驱动类已实现）、app/simulator.py、**docs/protocol.md**。
config.yaml 里的 transport 可选 serial 或 simulator。

## 目标
在 tools/ 下新增三个调试脚本，每个都能**独立运行**、**输出人能直接看懂的结论**：
  tools/debug_light.py      调试光照度变送器
  tools/debug_ultrasonic.py 调试超声波模组
  tools/debug_alarm.py      调试声光报警器

> ⚠️ 下面提到的寄存器、取值范围、量程含义等，**一律从 `docs/protocol.md` 里查**。
> 脚本里不要出现任何"来历不明"的数字：用到的地址和取值范围都要能从摘要里找到依据，
> 并写成常量 + 注释注明出处。

## 共同要求
1. 都支持 `--transport serial|simulator` 覆盖 config.yaml，以及 `--port` `--baud` `--slave` 覆盖。
2. 输出用清晰的分节标题、缩进和符号（✓ / ✗ / ⚠），不要刷一大坨原始日志。
3. 每个检查项都要打印：做了什么 → 期望 → 实际 → 结论。
4. 结束时打印一份汇总：通过 x 项 / 失败 y 项，并给出「下一步建议」。
5. 任何异常都要被捕获并转成友好提示，脚本不能崩。
6. 退出码：全部通过返回 0，有失败返回 1（方便以后接 CI）。

## tools/debug_light.py
依次做：
1. 连接设备（打印实际用的串口/TCP、波特率、从机地址）
2. 读**测量用的那几个寄存器**（地址与个数取自摘要），打印原始十六进制，
   并按摘要里的换算公式换算成物理量打印
3. 连续采样 5 次（间隔 0.5s），打印每次的值，算 min/max/平均，判断数值是否稳定
4. 读设备地址寄存器与波特率寄存器，并**按摘要把波特率代码翻译成人话**（代码→bps）
5. 【只读，不修改】提示用户「如需修改地址/波特率请手动确认后再执行」

## tools/debug_ultrasonic.py
依次做：
1. 连接设备
2. 读测量区，分别解析出：处理值距离、实时值距离、温度
   —— 温度**先看摘要确认是不是有符号量**，并明确打印出你是否做了符号处理
3. 读回波时间寄存器，按摘要的换算方式换算成 mm，与两个距离值对比一致性（允许误差 ±5mm）
4. 连续采样 10 次（间隔 0.2s），统计 min/max/平均，并统计**摘要里标注的异常值**各出现了几次
5. 读配置项（角度等级 / 降噪等级 / 量程等级等，以摘要为准），
   并**按摘要给出的含义**把等级翻译成人话（角度对应多少度、量程对应多少 cm）
6. 给出判断：量程等级与当前实测距离是否匹配（距离接近量程上限时应建议调大等级）

## tools/debug_alarm.py
依次做：
1. 连接设备（注意：摘要里若有命令最小间隔的要求，基类已通过 gap_ms 处理，这里要打印确认）
2. 读状态区，解析并打印：声音开/关、灯光开/关、音量、曲目(文件夹-曲目)、播放模式、闪烁模式
3. 读"总曲目"寄存器并打印（文件夹数 / 曲目数）
4. 【交互式测试，默认先预告再执行】依次执行并每次读回确认：
   · 全开 → 改音量 → 改音量到上限 → 改闪烁模式 → 全关
   （用摘要里的合法取值；每步之间自动 sleep 0.5s；每步都打印「写入前 → 写入后」的对比）
   ⚠️ 这个脚本会**真的让报警器响**，请在脚本开头打印醒目提示，并要求加 `--yes` 参数才真正执行写操作；
      不带 `--yes` 时只做读取和展示（dry-run）。
5. 最后**恢复到摘要里记录的出厂默认状态**并读回确认
````

## 四、验收清单：AI 交上来的驱动，怎么判断对不对

> **这一节故意不给答案。** 答案在 [导读 · 附录 A](/2026/09/16/AI学习/传感器监控平台/README/) 里——但**那是给验收者用的**，
> 请先自己核对完，再去看附录确认。
> 本项目要训练的能力，正是「**让 AI 去读文档、再由你核对**」这一环。

| # | 要问 AI 的问题 | 判断标准 |
| :---: | :--- | :--- |
| 1 | 光照度的量程有多大？单个寄存器装得下吗？ | 如果它只读 1 个寄存器，追问一句"量程上限是多少" |
| 2 | 温度这个量，文档写的是有符号还是无符号？ | 让它把文档原句贴出来，再看代码有没有做符号处理 |
| 3 | 某个测量值是怎么换算成物理量的？ | 换算系数必须能在文档里找到出处，不能是"经验值" |
| 4 | 有没有"特殊含义"的取值？ | 这些值要翻译成状态，而不是当成正常数值用 |
| 5 | 报警器状态寄存器是整体数值还是位域？ | 单独改一个功能时，另一个功能不能被带偏 |
| 6 | 音量的合法范围是多少？ | 越界要有校验和明确报错，不能静默写入 |
| 7 | 有没有"命令最小间隔"这类时序约束？ | 约束要落在 `gap_ms` 上，而不是散落一堆 `sleep` |
| 8 | 采集线程和控制接口同时用串口会怎样？ | 必须共用一把锁，否则两边都 CRC 错 |
| 9 | 这些地址和公式，出处写在哪？ | 每个常量旁边都要有注释指向文档/摘要 |

## 七、常见问题

**Q1：`read_holding` 一直返回 None？**

- **用模拟器时** → 先确认模拟器还在跑（跑它的终端里还有监听信息；不在了就重启它），
  再跑 [第 2 篇](/2026/09/16/AI学习/传感器监控平台/02-串口链路打通与模拟器/) 的 `scan_slaves.py` 确认链路；
- **接真机时** → 先翻 [第 3 篇](/2026/09/16/AI学习/传感器监控平台/03-真机接入与总线组网/) 的排错手册。
  十有八九是**地址冲突、没共地、或波特率没统一**，而不是代码问题。

一句话：**链路不通，驱动再对也读不到东西。**

**Q2：某个测量值读出来是单个寄存器装不下的量级，怎么办？**
**先回文档。** 多数量程很大的量会跨两个寄存器（高字 + 低字），
先用高字左移再或上低字；也可能反过来。**顺序以 `docs/protocol.md` 为准，不要试出来的结果当结论。**

**Q3：报警器写入后只响灯、不响声音？**
先怀疑两件事：**位定义是否用对**、**是不是买到了另一个型号**。
厂商文档里通常写了多种型号的差异——先翻回去确认你的设备属于哪一种。

**Q4：并发跑久了偶尔报 CRC 错误？**
九成是**没加锁**——采集线程和控制接口同时用了串口。检查是否所有读写都走了基类的锁。

**Q5：模拟器里能跑，接上真机就不行？**
模拟器不会模拟**接线问题**。按 `scan_slaves.py --baud-scan` 走一遍，重点查 A/B 是否接反、供电是否足够。

**Q6：AI 说"文档里没写"，我该怎么办？**
先让它**把你怀疑的那段原文贴出来**，很多时候是它没读到、或读到了却没看懂。
确实没有，就让它按最保守的方式实现并标注 TODO，或者联系厂商要补充文档——**不要让它猜**。
